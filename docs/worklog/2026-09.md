## 2026-09-02

### 批次匯入異常資料待審機制上線

新部門/新資料上線自動化任務的一環：批次匯入資料若有異常（格式錯誤或欄位缺值），改為標記待審不擋整批匯入，交由後台人工審核決定接受或拒絕。新增獨立表 `pending_alarm_imports`，比照既有建議審核（`AlarmSuggestionStore`）的架構。

過程中修復了兩個並發相關的問題：
- 審核類操作（建議審核、待審匯入審核）原本是「先檢查狀態→寫入→更新狀態」，中間有競態窗口；改成 claim-first（CAS 條件式更新放最前面，成功才動作，失敗要 release），accept/reject 兩條路徑對稱處理，抽出共用 `StatusTransitionMixin`。
- 語意審核（303 筆待套用修正）的復原快照防呆：補上 `is_available()` 檢查，避免快照機制不可用時仍誤放行操作。

### 路由重導向安全問題發現與完整修復（本日主線）

**發現起點**：QA 在做批次匯入端到端驗收時，親手重現了一個資料完整性問題——核准一筆 `device_model` 缺值的異常資料後，空字串被寫入正式 `alarms` 表，且這筆資料透過正常 DELETE API 完全刪不掉（命中 Flask/Werkzeug 既有的路由陷阱：`<string>` 路徑段不匹配空字串，連 view function 都進不去，直接 404）。

**追查中意外發現更嚴重的問題**：QA 為了寫路由空段測試，進一步發現 Flask 的 `merge_slashes`（預設開啟）會把含 `//` 的請求自動重導向到另一個完全不同的端點，且 308 重導向會保留 HTTP method 與 body、權限檢查發生在重導向**之後**。QA 實際重現了具體案例：對空部門 ID 呼叫「重設密碼」端點，被合併斜線重導向到「改名部門」端點。這次操作（改名）確實真的執行成功了（HTTP 200，`rename_department()` 的業務邏輯真的跑完），沒有造成實際資料異動是因為 QA 測試用的部門 ID 本身在正式環境不存在——如果攻擊者選一個真實存在的部門 ID，這個改名操作會真的生效。兩端點權限剛好相同這件事，防的是「重導向繞過更高權限要求」這個更嚴重的情境，但這次的執行本身不是被權限擋下來的，是操作對象剛好是空的——不能把僥倖講成安全機制生效。

過程中 QA 跟老師都各自在本機重現/驗證時，差點對正式 Supabase 環境發出真實寫入請求，原因是 `DepartmentStore` 是全系統唯一沒有測試環境隔離機制的 Store 類別。兩人都主動誠實揭露這個疏失並查證確認沒有造成實際資料異動。

**修復過程**：
1. `app.url_map.merge_slashes = False` + `before_request` 攔截含 `//` 的路徑直接 404
2. 新增碰撞掃描腳本 `scripts/check_route_collisions.py`，自動掃描「路由拿掉一個動態段後會不會意外命中另一條路由」；掃出 17 組碰撞，老師逐類實測分類（8 組是靜態檔案路由的假警報、6 組碰撞後權限反而變嚴格不構成風險、1 組跟業務邏輯無關、2 組是真正需要處理的部門管理端點碰撞）
3. `_guard_production_write()` 護欄：本機環境預設拒絕對正式環境的寫入操作，需明確設環境變數才能放行
4. `DepartmentStore` 改為在非 Supabase 環境明確拋出 RuntimeError 拒絕操作，而非降級成本機測試模式（降級會讓測試通過但驗證不到任何東西，因為部門機制在單租戶模式下沒有語意）
5. 部門管理的 reset-password/active 端點重構：第一版合併方案只是換了碰撞對象沒解決根因，改用 `department-actions` 路徑（動態參數放路徑最後一段、前綴字面量不跟其他路由重疊），結構性消除碰撞可能

**驗收**：QA 對重構後的端點做了完整黑箱驗收（密碼真的改變且能用新密碼登入、啟用停用真的生效），且用 Supabase REST API 精確寫回原始密碼雜湊值還原測試帳號，而非重設明文密碼（雜湊值會不同，無法真正還原）。QA 另外用自己先前真正犯錯的確切操作條件重放，確認 `_guard_production_write()` 在最貼近真實情境下確實生效。老師複查碰撞掃描結果、複查修復內容，確認結構性解決而非表面繞開。

**過程中的額外發現（記錄為獨立待辦）**：QA 驗收時發現部門管理高權限端點（改名/改密碼/停用啟用）完全沒有稽核紀錄（audit log）。老師複查確認這是既有缺口，不是本次重構造成的，不阻塞本次收尾。使用者裁決另開一輪處理。

**結案**：commit `618e423`，398 測試全過，working directory 乾淨。CLAUDE.md「已知陷阱」章節已補完整教訓記錄，供之後任何人參考。

### 團隊工作日記機制建立

使用者提議開始寫工作日記，老師提出分工方案並經確認定案：

- 分工：員工負責彙整寫入與 commit；顧問負責整理跨任務脈絡摘要；老師負責複查技術/邏輯敘述準確性；醫生負責複核 production/正式環境狀態敘述是否吻合實際
- 跟既有文件的分工：CLAUDE.md 記「現在的規則」、memory 記「AI 要記得的跨 session 結論（按主題）」、日記記「發生過什麼、怎麼發生的（給人看，按時間）」，三者互相連結不互相複製內容
