# 系統現況總覽（截至 2026-09-02）

> 這份是給 `docs/worklog/` 開頭用的「系統目前完成到哪裡」快照，不是流水帳。定位：讓任何人（包含新加入的協作者）花五分鐘看完就知道系統現在能做什麼、還缺什麼。細節請對照 memory 系統或對應 commit，這裡只列結論。

## 系統是什麼

工廠設備警報查詢系統（Alarm-System）。核心功能是讓現場人員能查詢設備錯誤代碼對應的原因/處置方式，並支援拍照辨識、多部門隔離、後台管理。正式環境部署在 Render，資料庫用 Supabase。

## 已完整上線的主線功能

### 警報查詢核心
- 多部門資料隔離（`department` 參數必填，`resolve_target_department()` 只讀 URL path）
- variant（機種變體）欄位支援，走 query string 而非路徑段（刻意設計，避免跟路由碰撞——見下方「路由重導向安全問題」）
- 代碼查詢的 normalize 邏輯統一收斂到後端，前端不再自行處理，避免不同代碼被誤判為同一筆（2026-09-01 結案）

### 拍照辨識（AI 分析）
- Gemini AI 拍照辨識設備錯誤代碼，含白名單機種驗證（fail-closed 機制）
- 500/503 錯誤有妥善的前後端處理（errorhandler + 前端用 `r.ok` 判斷，不再籠統吞錯）（2026-09-01 結案）
- MEM/LOG 兩層寫入用 try/finally 保證任一步驟失敗都會記錄，不會靜默漏記
- 已知效能瓶頸：單次辨識約 29 秒，主要耗時來源是 Gemini API 呼叫本身；已修正一個排序正確性缺陷（`_sb_query()` 補 `order` 參數），效能優化方向仍在等分段計時數據評估（進行中，未決）

### 後台管理
- 部門管理（新增/改名/密碼重設/啟用停用/刪除）
- 部門刪除防護：伺服器端強制筆數比對，操作者需先看過受影響筆數並回傳確認
- 批次匯入（CSV/Excel/JSON）：從「遇錯即停」改為「收集單列錯誤、其他列繼續解析」，格式異常的個別列標記待審不擋整批，結構性錯誤（機種不存在等）仍整批擋下
- 異常匯入資料獨立待審機制（`pending_alarm_imports` 表），比照既有建議審核（`AlarmSuggestionStore`）模式
- 效能優化：登入併行化、dashboard 分批載入、部門層級 TTL 快取（含跨部門隔離安全驗證）（2026-08-27 定案並上線）

### 資料完整性與安全防護
- 孤兒資料防護：`upsert_one()` 拒絕空字串主鍵（variant 欄位除外，空字串是其合法語意）
- 狀態轉換的 TOCTOU 並發競態修復：審核類操作（建議審核、待審匯入審核）改用 claim-first（CAS 條件式更新），抽出共用 `StatusTransitionMixin`
- **路由重導向安全問題**（2026-09-02 完整結案，commit `618e423`）：
  - Flask `merge_slashes` 預設行為會讓含空路徑段的請求被自動重導向到另一個端點，可能繞過權限檢查；已關閉 `merge_slashes` 並攔截 `//` 路徑
  - 新增碰撞掃描腳本（`scripts/check_route_collisions.py`），系統性找出「路由某段消失後會不會意外碰撞另一條路由」
  - 部門管理的 reset-password/active 端點重構為 `department-actions`，結構性消除路徑碰撞風險
  - `DepartmentStore`（原本是唯一沒有測試環境隔離的 Store 類別）改為在非 Supabase 環境明確拒絕，不降級
  - 新增 `_guard_production_write()` 護欄，本機預設拒絕對正式環境寫入

## 已知但暫緩/待辦的項目

- **孤兒資料防護方案 4、5**：孤兒資料對帳查詢、`/api/admin/orphans` 診斷+purge 補救端點——因路由重導向問題插隊而暫停，待恢復
- **部門管理端點缺乏稽核紀錄（audit log）**：改名/改密碼/停用啟用完全沒有 audit log，是既有缺口非新問題，使用者裁決另開一輪處理
- **語意品質掃描（音譯/翻譯品質）**：只是離線 CLI 工具，從未整合進正式匯入流程，新資料匯入不會自動觸發，使用者裁決維持現狀、全靠人工記得手動跑
- **AI 拍照辨識信心度過低自動進待審核**：新需求提案，使用者裁決先放一邊
- **拍照辨識效能優化**：等分段計時數據，評估「省查詢」方向是否值得做
