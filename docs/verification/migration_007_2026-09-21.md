# Migration 007（import_snapshots）正式環境實地驗證報告

**日期**：2026-09-21
**驗證者**：老師（本session）
**驗證方式**：對正式 Supabase 環境實地執行 `commit_rows()` → `undo_snapshot()`，非單元測試/mock

## 背景

- migration 007（`import_snapshots`/`import_snapshot_rows`）先前只準備好 SQL，長期未在正式環境執行（醫生用 curl 實測確認 404，證實 DDL 從未生效）。
- 使用者已於今日在 Supabase Dashboard 執行完成該 migration。
- 這是 LINE 3 方案 v3 第 5.3 節「kill switch 開啟條件之一」，也是獨立於 LINE 3 任務、優先處理的既有生產環境缺口。

## 驗證方法

新建一個一次性、`hidden=True`、`purgeable=True` 的測試部門（`zzverify<timestamp>`），完整流程只在此隔離部門內操作，不觸碰任何既有部門/資料，結束後用 `purge_department()` 徹底清除。腳本存於 `scratchpad/verify_migration007.py`。

## 驗證步驟與結果

| 步驟 | 動作 | 結果 |
|---|---|---|
| 1 | 建立測試部門 | 成功，`hidden=True`、`purgeable=True` |
| 2 | `ImportSnapshotStore.is_available()` 探測 | `True`——確認 `import_snapshots` 表在正式環境真的存在 |
| 3 | 新增測試機種 | 成功 |
| 4 | `commit_rows()` 寫入 1 筆測試警報 | 成功，`snapshot_id=1` 已建立 |
| 5 | 確認警報已寫入正式 `alarms` 表 | 確認存在 |
| 6 | `undo_snapshot(1)` 執行復原 | `{"found": True, "already_undone": False, "succeeded": 1, "failed": 0}` |
| 7 | 確認警報已被復原 | 確認**已從正式 `alarms` 表刪除**（`get_one()` 回傳 `None`） |
| 8 | 重複呼叫 `undo_snapshot(1)` | 正確回傳 `{"already_undone": True}`，防重複復原機制生效 |
| 9 | `purge_department()` 清除測試部門 | 成功，`devices: 1`、`alarm_history: 1` 一併清除 |

## 資料庫層面最終核對（步驟 9 之後）

直接查詢正式 Supabase 確認：
- `departments`/`devices`/`alarms`/`alarm_history` 表：`zzverify*` 相關資料**殘留 0 筆**，測試部門完整清除，沒有污染正式資料。
- `import_snapshots` 表：保留 1 筆記錄（`id=1`），`undone_at` 已填、`undone_result={"succeeded":1,"failed":0}`——這是預期行為，`purge_department()` 本來就不清 `import_snapshots`（migration 007 設計為稽核軌跡，不隨部門刪除消失），這筆記錄本身就是本次驗證的書面證據。
- `import_snapshot_rows` 表：對應明細 `{"device_model":"ZZVERIFY_DEVICE","code":"ZZVERIFY_CODE_0001","before_data":null}`——`before_data=null` 正確代表這筆資料 commit 前不存在，undo 應執行刪除，跟實際行為一致。

## 結論

**migration 007 的復原機制在正式環境完整生效，非僅單元測試層級的驗證**：
1. 表已在正式環境正確建立，`is_available()` 探測邏輯正常
2. `commit_rows()` 寫入時正確建立快照
3. `undo_snapshot()` 真正把資料從正式表刪除（不是回傳假成功）
4. 防重複復原（`already_undone`）機制生效
5. 整個驗證流程對既有正式資料零污染

既有 `tests/test_bulk_import_undo.py`（7 個 mock 測試）驗證的是程式碼邏輯本身正確；這次驗證補上的是「migration 007 真的在正式環境執行過、且復原機制在真實資料庫上確實生效」這一層，兩者互補，缺一不可——這正是先前發現 migration 007 未執行的根本問題（單元測試全過但正式環境完全沒有這張表）。

LINE 3 方案 v3 第 5.3 節要求的「migration 007 已在正式環境執行，且完成一次 commit_rows()→undo_snapshot() 的實地還原驗證，驗證結果有書面記錄」，本報告即為該書面記錄。
