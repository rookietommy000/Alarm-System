## 背景與問題陳述

系統目前有兩條批次匯入路線：

- **Route B（標準範本）**：使用者依照系統提供的固定範本欄位順序填寫 CSV/Excel/JSON，`load_csv()`/`load_excel()`/`load_json()`（`backend/alarm_ingest/parse.py`）只認**第一列**為表頭，用 `_check_required_headers()` 比對必要欄位是否存在，格式不符直接 400 拒絕整份檔案。
- **Route A（inspect 智慧偵測）**：`POST /api/admin/import/<department>/inspect` 讀取原廠格式的 Excel，用 `detect_columns()`（`backend/alarm_ingest/detect.py`）自動猜測「代碼欄」「原因欄」「處置欄」在哪，供人工在 UI 上確認/修改欄位對應，再呼叫 `grid_to_rows()` 轉成標準資料列。**這條路線目前只做到「解析出資料」，沒有接上驗證與寫入邏輯（沒有 commit 端點）。**

新部門「LINE 3」提供了 5 份原廠 Excel（`22062QE5SP63_02.xlsx`、`22062QE6SP63_DB_01.xlsx`、`22062QE6SP63_DE.xlsx`、`22062QE6SP63_LF.xlsx`、`22062QE6SP63_RI.xlsx`），實際嘗試匯入後兩條路線都走不通：

- Route A 失敗：`detect_columns()` 只掃描前 5 列找關鍵字，找不到才 fallback 掃描前 20 列——這 5 份檔案的真實表頭都在第 58～75 列（前面是標題頁、修訂履歷、代碼圖例、運行模式圖例等說明區塊），完全落在掃描範圍之外。且即使偵測成功，Route A 也沒有 commit 能力。
- Route B 失敗：`load_excel()` 固定認第一列為表頭，直接被 `_check_required_headers()` 擋下回 400。

兩次嘗試都在解析階段被擋下，**沒有寫入任何錯誤資料**——既有防呆機制運作正常，是能力缺口不是 bug。

使用者裁決：系統要原生支援這種原廠格式，不要每次新部門上線都得手動把原廠 Excel 轉成標準範本格式再匯入。

**本輪對這項裁決的處理**：第三輪審查有一個視角主張「LINE 3 只轉一次，不值得蓋一整條新路徑，應該手動轉檔走 Route B」。這與使用者裁決直接衝突，不由工程端逕行推翻。本方案採取的折衷是：**原生支援的能力照做（尊重裁決），但拆成多階段交付，且 LINE 3 這一次的實際上線走「用階段二的純函式產出標準範本檔案，再跑既有 Route B」**——這樣 LINE 3 不必等階段三就能上線、既有防線全部生效，同時這次上線本身就成為映射表的實地驗證，等階段三的 commit 端點開放時，映射表已經被真實資料與現場使用驗證過。詳見「方案設計・零、交付分階段」。

> 真實資料筆數也一併重新精算：LF 表尾（第 64 列）是空白列，先前用「總列數 − 子表頭列」的減法公式（64−59=5）未扣除這一列，實際用 Alarm Number 欄位非空判斷應為 4 筆。其餘 4 份檔案筆數與統一公式後的既有記載一致，未變動。
>
> 此次查證同時附帶產出了下方「四、欄位映射表」與「4.5 跨檔案代碼碰撞」原本列為階段零待辦的部分結論（Alarm Type 值域、跨檔重複數、Alarm Number 值域），詳見對應章節與「仍待確認事項」的更新。查證所用腳本存於本次查證的 scratchpad 路徑（`verify_v3.py`），供之後回查或重跑。

**關鍵事實一：5 份檔案的表頭文字完全相同、一字不差**：

```
Alarm Type | Alarm Number | HMI Message | Alarm Description | Solution
| Alarm Simulation | Alarm Effects | Alarm Reset | Validation Test | Operating Modes
```

只有表頭出現的列數不同、Operating Modes 底下的子欄位數量不同。這代表這不是「表頭模糊、可能被埋沒在雜訊資料裡難以辨識」的情境，而是「已知固定文字表頭，只是出現位置比較深」——這個區分直接決定了偵測策略的選擇。

**關鍵事實二：只有「Operating Modes」這一欄是雙層表頭，其餘欄位都是單層**：

以 `22062QE6SP63_LF.xlsx` 為例（第 58～59 列，`merged_cells.ranges` 節錄）：

```
row58: ['Alarm Type', 'Alarm Number', ..., 'Operating Modes', None]
row59: [None, None, ..., None, 'PROD', 'MM']
merged: A58:A59, B58:B59, C58:C59, ...（前 9 欄垂直合併，跨兩列但只有一層語意）
merged: J58:K58（Operating Modes 橫向合併，J59='PROD'、K59='MM' 才是真正的子欄位）
```

前 9 欄用垂直合併讓表頭「視覺上」跨兩列，語意上只有一層；只有 Operating Modes 需要「母表頭 + 下一列子表頭」兩層才能得到完整意義，子欄位數量因檔案而異（2～5 個）。

**關鍵事實三：資料本身乾淨，沒有合併儲存格污染資料列**：抽查每份檔案表頭列之後的資料列，欄位與欄位之間沒有交叉合併，可以直接逐列逐欄讀取。

**關鍵事實四（第三輪查證修正，已實測，見 4.5）**：這 5 份檔案的 `Alarm Type` + `Alarm Number` 組合**跨檔案完全不重複**（214 筆資料，重複數＝0）。原文件曾列為「必須在階段零補上」的未知項，本輪已用 `openpyxl` 逐檔讀取後統計得出。5 份檔案要匯進同一個部門，這個系統的歷史事故（QATEST01/0001/ZZC001）正是警報代碼碰撞，因此這個結果值得記錄，但**不代表以後新增檔案時可以省略這項檢查**——本方案 4.5 節要求的「轉出時偵測重複並報錯中止」機制仍然要做，這裡確認的是「這一次這 5 份檔案」的既有事實，不是「這條路徑永遠不會撞」的保證。

**關鍵事實五（第三輪查證修正，已實測，見 4.1）**：`Alarm Number` 欄位 5 份檔案的實測值全部是**純整數**（Python `int` 型別，例如 `2945`、`1153`），沒有字母前綴或分隔符。可用正規式 `^\d+$` 判斷，不需要停留在「非空且非說明性長句」的啟發式（見「一、1.2」條件 B）。

## 現有程式碼的相關實作（已讀取確認，非推測）

- `detect_columns()`（`detect.py:84-133`）：「先在前 5 列找關鍵字命中，命中後往下數是否有 ≥5 列以代碼格式開頭；找不到則 fallback 掃描前 20 列統計『哪一欄最常以代碼開頭』」。fallback 是為了應付「完全沒有表頭、或表頭被合併儲存格吃掉」的情境。docstring 記載一個真實踩過的坑：某分頁是問答清單、內文提到代碼格式但不是警報資料，被 fallback 誤判，後來加上 `MIN_CODE_ROWS`（至少 5 列連續符合代碼格式）這個防呆閾值。
- `grid_to_rows()`（`detect.py:137-156`）：輸出 `{"code", "variant", "cause", "action", "_source"}`——**與標準匯入路線 `row_to_alarm()`（`parse.py:72-116`）輸出的標準 alarm dict（`code`/`device_model`/`severity`/`description`/`cause`/`solution`/`local_solution`/`keywords`/`sol_steps`）不同**，缺少 `device_model`、`description`、`solution`，且用 `action` 不是 `solution`。這是既有的 schema 落差。
- `_bulk_import_validate()`（`app.py:880` 起）與 `commit_rows()`（`commit.py:31` 起）：Route B 的驗證與寫入邏輯，只吃標準化後的 rows（不管來源是 CSV/Excel/JSON），包含機種存在性檢查（`validate_devices_exist()`）、variant 啟用狀態一致性檢查（`decide_variant_mode()`/`check_variant_consistency()`）、完整度攔截（`completeness_report()`）。**不應該為 Route A 另外複製一份。**
- Route A 目前的端點：`inspect`（`app.py:1126` 起，唯讀）、`split`（`app.py:1202` 起，AI 輔助拆分文字，不碰資料庫）。**沒有 commit 端點。**
- `bulk_import_commit()`（`app.py:1029-1030`）的裝飾器是 `@admin_required`，不是 `@superadmin_required`——部門資料匯入在權限模型裡是**部門層級操作**。

## 方案設計

### 零、交付分階段（第三輪新增，取代原本的單一綁定式交付）

原方案把「深層表頭解析」與「Route A 補上 commit 能力（新端點 + 新 UI 流程 + migration）」綁成同一份交付。第三輪審查五個視角一致認為應該拆開：任何一段卡住，已經可用的能力也上不了線；而寫入能力的風險遠高於解析能力，綁在一起等於讓低風險的部分承擔高風險部分的 release gate。

| 階段 | 內容 | 風險 | 前置條件 |
|---|---|---|---|
| **階段零** | 用 openpyxl 產出映射表 v0 草稿、精算各檔真實筆數、核對 DE 的子欄位、確認各檔子表頭列位置、算出 `Alarm Number` 的值域與代碼格式、計算跨檔 `code` 重複數、確認 `device_model` 來源與檔名對照、抽樣 Alarm Effects/Simulation/Reset/Validation Test 的值、確認欄位內容語言。**無程式碼變更。** | 零 | 無，現在就能做 |
| **階段一** | 深層表頭偵測分支 + Operating Modes 展開 + 5 份 fixture 正向測試 + 既有檔案負向/迴歸測試。**只動 `detect.py`，唯讀，不寫入資料庫。** | 低 | 階段零的筆數精算、DE 子欄位核對、`Alarm Number` 代碼格式 |
| **階段二** | 映射表定稿（人工逐欄確認）+ `grid_to_rows()` 輸出收斂為標準 alarm dict 的純函式 + 單元測試。**仍不寫入資料庫。** | 中（語意風險集中於此） | 階段零、階段一 |
| **階段二・五** | **LINE 3 本次實際上線**：用階段二的純函式把 5 份檔案轉出標準範本檔，走**既有 Route B** 的 preview/commit 匯入。同階段先做完偵錯回路的前兩項（資料來源標註、現場回報入口），再依 canary 順序匯入。 | 中（但既有防線全數生效） | 階段二；migration 007 已實地驗證還原（見 5.3） |
| **階段三** | Route A 專屬 commit 端點 + UI 欄位對應確認流程 + `operating_modes` migration 與顯示 + 快照留痕 + kill switch + 跨部門 schema 迴歸測試。 | 高 | 見 5.2 的 kill switch 開啟條件 |

**為什麼加入「階段二・五」**：它同時滿足使用者「不要手動轉檔」的裁決精神（轉檔由階段二的程式碼自動完成，不是人工複製貼上）與審查者「這次不該為一次性需求蓋新寫入路徑」的顧慮（寫入走既有已驗證的 Route B）。副作用是這次上線本身就是映射表的實地驗證，階段三開放時映射表已非紙上推測。

**`operating_modes` 的處理**：這個欄位在階段二・五走 Route B 時無處可放——Route B 的標準範本沒有這欄，且 migration 尚未執行。因此**階段二・五 先不匯入 `operating_modes`**，留給階段三；階段二的純函式仍然解析並輸出它，只是轉出標準範本時略過。（階段三要不要在前台顯示它，是另一個決定，見「二、Operating Modes」末。）

**`device_model` 的處理**：階段二・五 走 Route B，`device_model` 是必填、且 `_bulk_import_validate()` 第一道就是機種存在性檢查，但這個值不在原廠檔案裡（見 4.4）。階段二・五 的做法是**由轉檔腳本的參數顯式指定，每個檔案一個機種**，值來自階段零的檔名對照結果、經部門 admin 確認後填入，**不由腳本自行從檔名推斷**。階段三的 UI 指定機制（見七）是這個做法的介面化版本，不是它的前置。

### 一、表頭偵測：新增「精確表頭組合比對」分支

現有 `detect_columns()` 的兩段式邏輯（前 5 列關鍵字比對 → fallback 前 20 列代碼統計）繼續保留，服務「表頭模糊或缺失」的既有情境。新增一個獨立分支服務「有清楚固定表頭、但位置較深」的情境。

**v2 版此處有三個缺陷，本輪修正**（詳見文末審查發現 F1–F3）：

#### 1.1 觸發順序：新分支放在**最前面**，不是最後

v2 寫「現有兩段式邏輯都失敗之後才啟用」。改為**新分支優先嘗試**，理由：

- 新分支是「整格文字精確等於已知表頭片語、且同列命中多個」的高確信判準；現有 fallback 是「統計哪一欄最常以代碼開頭」的低確信猜測。讓低確信的邏輯先跑，可能在深層表頭檔案上猜出一個**錯的但通過 `MIN_CODE_ROWS` 的答案**，新分支就永遠不會被觸發——把高確信的判準排在低確信之後，是把順序弄反了。
- 對既有情境零影響：FILL203 那類檔案不會有 6 個（含）以上英文精確片語出現在同一列，新分支會直接落空並把控制權交還既有邏輯。這個「零影響」不是推論，**必須由階段一的迴歸測試實際斷言**（見「六、測試策略」）。

最終順序：**精確表頭組合比對（新）→ 前 5 列關鍵字比對（既有）→ fallback 前 20 列代碼統計（既有）**。

#### 1.2 判準：三個條件同時成立，不是單一 N 值

```
對表格的每一列（上限為該檔案實際列數；Excel 不是無限大，不另設人工上限）：

條件 A（精確等值）：該列中，「整格文字正規化後恰好等於」已知表頭片語的儲存格數量 ≥ 6
    正規化 = 去頭尾空白 + 連續空白合併為一 + 去換行 + 全形轉半形 + 大小寫不敏感
    ※ 用「整格等值」而非「包含」，是最有效的一道防線：
      圖例區塊的儲存格通常是「Alarm Type：警報類型代碼說明」這種句子，
      整格等值比對會直接排除，不需要靠機率論證。

條件 B（後置資料驗證，對應既有 MIN_CODE_ROWS 的精神，但門檻不能照抄 5）：
    候選列往下（跳過子表頭列）的非空列中，
    「Alarm Number」對應欄位為非空且非說明性長句的比例 ≥ 80%，且至少 1 列。
    不通過則此候選列作廢，繼續往下找。

條件 C（選擇規則）：不取「第一個命中列」。
    取「通過 A 與 B、且條件 A 命中數最高」的列；
    命中數相同時取列號較大者（說明性圖例通常在真表頭之前）。
```

**閾值為什麼是 6 而不是 v2 的 4**：已知表頭是 10 個精確片語且 5 份檔案一字不差，把門檻從 4 拉到 6 幾乎零成本（真表頭永遠命中 10），卻明顯縮小誤命中空間。保留 6 而非要求 10，是留給原廠日後增減一兩欄的餘裕。

**條件 B 為什麼不能省**：v2 版的新分支完全沒有等價於 `MIN_CODE_ROWS` 的後置驗證，等於把既有邏輯用一次真實誤判換來的教訓丟掉。而這 5 份檔案的前段明確包含「代碼圖例」「運行模式圖例」說明區塊——圖例區塊最常做的事就是逐欄複述欄位名稱，正是最可能誤命中的地方。

**條件 B 的門檻為什麼不是既有的 `MIN_CODE_ROWS`（5 列）**：`DB_01.xlsx` 表頭後只有 3 列資料、`LF.xlsx` 只有 5 列。照抄「≥5 列」這個為大檔設計的絕對門檻，DB_01 的真表頭永遠通不過驗證、整份檔案偵測失敗，LF 則是零餘裕——只要有一列是空白就跟著失敗。改用比例判準才能同時容納 3 筆與 96 筆的檔案。**`DB_01.xlsx` 的 3 筆資料是這個門檻的已知反例，任何人日後想把它改回絕對筆數之前，先看這一段。**

**條件 B 的判準（第三輪查證修正，已定案）**：「符合代碼格式」原本依賴階段零才產出的 `Alarm Number` 值域與正規式（關鍵事實五）。本輪已實測 5 份檔案的 `Alarm Number` 全部是純整數，可直接採用正規式 `^\d+$` 判斷，不需要先以「非空且非說明性長句」的啟發式過渡。若日後新增的原廠檔案 `Alarm Number` 出現非純整數格式（例如帶字母前綴），這個正規式需要重新檢視，不是自動涵蓋所有未來案例。

**v2 版那句機率論證應予撤回**：v2 寫「多個精確片語同時在同一列出現的巧合機率本質上遠低於單一寬鬆詞」。這句話在數學上沒錯，但它被用來取代防呆設計，而且樣本支撐薄弱——5 份檔案來自同一原廠、同一模板，有效樣本量實質是 1。機率論證不能替代條件 B。

#### 1.3 已知限制

這組關鍵字是從 LINE 3 這 5 份檔案觀察到的固定文字。要支援「未來其他原廠格式使用不同措辭的固定表頭」需要擴充關鍵字組。本輪只涵蓋這組已驗證的關鍵字，**不做成可配置的通用系統**——只有一個樣本，做成通用系統是過度設計。關鍵字清單放在 `detect.py` 的模組常數，並在註解寫明來源與新增方式。

### 二、Operating Modes 雙層表頭：動態展開 + jsonb 陣列儲存

**偵測邏輯**（v2 版此處有兩個未定義行為，本輪補上）：

1. 掃描到表頭列後，檢查該列是否有一欄整格文字為 "Operating Modes"。
2. **子欄位的欄範圍由該儲存格的橫向合併範圍決定**（例如 `J58:K58` → 欄 J 到 K），不是 v2 寫的「從該欄開始往右的所有非空儲存格」。v2 的寫法沒有定義右邊界——這 5 份檔案剛好 Operating Modes 是最後一欄所以沒出事，但只要原廠日後在後面加一欄，就會把那一欄誤吃進來。合併範圍這個資訊文件自己已經讀出來了（關鍵事實二），拿來用即可。若該儲存格沒有橫向合併（單一子欄位的情形），則子欄位範圍即該欄本身。
3. 讀取子表頭列在該範圍內的非空儲存格作為子欄位名稱清單（PROD/MM，或 PREP/PROD/PE/MM/CS，依檔案而定，不寫死數量）。
4. 對每一筆資料列，讀取這些子欄位位置的值，**只保留「啟用」的子欄位名稱**組成陣列。

**「啟用」的判定規則（v2 未定義，本輪補上）**：

- 正規化後（去空白、全形轉半形、大小寫不敏感）等於 `x` → 啟用
- 正規化後為空字串、`-`、`—`、`n/a` → 未啟用
- **其他任何值 → 不得靜默丟棄**，必須計入解析警告並在 preview 階段顯示給操作者（例如原廠用 `✓`、`O`、或寫了備註文字）。靜默丟棄一個看不懂的值，等於默默把「這個警報在某模式下會觸發」變成「不會觸發」。

**空陣列與缺席的區分（v2 未定義，本輪補上）**：

- `[]`（所有模式都未啟用）與 `null`（這份檔案根本沒有 Operating Modes 欄）在 `OPTIONAL_FIELDS`「缺席時不覆蓋既有值」的邏輯下**必須明確區分**：`[]` 是有意義的值，要寫入並覆蓋；`null` 才是缺席，不覆蓋。
- 這不是假想情境：測試策略本來就要求挑一筆「都沒啟用的」資料，那筆就是 `[]`。

**儲存方式**：比照 `keywords`/`sol_steps` 的既有做法，新增獨立欄位 `operating_modes`（jsonb，nullable，存字串陣列）。這代表：

- 需要新的 migration 幫 `alarms` 表加這個欄位（比照 `006_add_variant.sql` 的慣例，DDL 準備好但不自動執行）。
- `ALARM_FIELDS`（`parse.py:26`）與 `OPTIONAL_FIELDS` 新增這個欄位。這是**跨部門共用的 schema 變更**（見審查發現 F7），**階段三**的迴歸測試必須涵蓋「既有部門走 Route B 匯入不受影響」（階段一不動 `parse.py`，沒有 schema 變更可迴歸）。
- **UI 顯示的取捨**：v2 說「先只做資料儲存、不做顯示，避免範圍蔓延」。第三輪審查對此有實質分歧：一方認為這是把最有價值的新維度丟進抽屜（現場人員最想知道「我這條線現在在 PROD 模式，這個警報關我什麼事」）；另一方認為存了不顯示，等於讓現場看到不完整的處置情境、且多一個要維護的欄位。**本輪裁決：階段三做儲存，同一階段內最小限度地顯示**——警報詳情頁加一行「適用運行模式：PROD、MM」，沒有這批資料的警報不顯示這一行。理由是「存了不顯示」在這個系統的歷史裡正是 migration 007 那種灰色地帶的原型；顯示一行文字的成本遠低於讓一個欄位懸在那裡。

### 三、Route A 補齊到能真正 commit（階段三）

核心原則：**Route A 與 Route B 的差異只應該存在於「怎麼把原始檔案轉成標準 rows」這個解析階段，驗證與寫入階段完全共用。**

1. 讓 Route A 解析的最終步驟（`grid_to_rows()` 的新版本）輸出與 Route B 完全相同的 schema（`row_to_alarm()` 的標準 alarm dict）。現有版本只認「代碼欄/原因欄/處置欄」三個角色，需擴充為完整映射（見「四、欄位映射表」）。**這一步是純函式，在階段二完成並單元測試，不依賴任何端點。**
2. 新增**獨立的** commit 端點，內部直接呼叫既有的 `_bulk_import_validate()` → `commit_rows()`，不重新實作機種存在性/variant 一致性/完整度攔截。**不在既有端點加條件分支去區分兩種來源**——這個系統過去因為「同一個函式裡用隱式狀態分岔不同呼叫來源的行為」踩過靜默失敗的坑（見 CLAUDE.md「例外處理判準」），兩條路線在 commit 這一步是「呼叫同一段驗證/寫入邏輯」，不是「同一個端點內部用 if 分岔」。
3. UI 流程：inspect（偵測+顯示）→ 人工確認/修改欄位對應（含 Operating Modes 子欄位確認）→ preview（呼叫 `_bulk_import_validate()`）→ commit（呼叫 `commit_rows()`）。比 Route B 多了「人工確認欄位對應」這一個前置步驟，UI 設計見「七、欄位對應確認介面」。

### 四、欄位映射表：從「待定項」提升為階段零的前置產物

第三輪審查的最強共識：**v2 把欄位映射寫成「硬性 release gate」，但那張表根本還不存在。一個沒有內容的關卡擋不了任何東西。** 整份方案的偵測、commit、快照、kill switch 全部繞著這張空表建，順序反了。

因此本輪把映射表提前到階段零，作為所有後續工作的前置產物。以下是**工程端能提供的草稿與判別準則**，標註信心水準；標「必須人工確認」的項目不由工程端或 AI 決定。

#### 4.2 HMI Message 與 Alarm Description 的判別準則

這兩欄哪個是 `description`、哪個是 `cause`，不能憑欄位名決定。階段零抽樣時用這個準則判讀：

- 若欄位內容是**條件句**（「當 X 感測器讀值超過 Y 持續 Z 秒時觸發」「馬達過載保護動作」）→ 這是觸發原因，對應 `cause`。
- 若欄位內容是**名詞短語或 HMI 畫面上原樣顯示的那行字**（「Feeder 2 Jam」「溫度異常」）→ 這是警報本身的描述，對應 `description`。
- 若兩欄都是條件句、或都是名詞短語 → 表示其中一欄沒有標準欄位可對應，寧可留空也**不要硬塞**。

#### 4.3 Alarm Effects 為什麼不塞進 `keywords`

v2 把「Alarm Effects 要不要對應到 keywords」列為待定項。本輪明確建議**不要**：

- v2 記載的樣例值是 `BZ`、`CFR`（這是 v2 待定項裡的一個舉例，**不是系統性抽樣的結果**，也沒有人核對過它們是否對應檔案前段的代碼圖例）。**若**階段零確認整欄都是這類縮寫代碼，那就不該塞進 `keywords`：`keywords` 是搜尋用的詞彙陣列，而需要圖例才能解讀的縮寫塞進去，使用者搜尋 `BZ` 得到的命中對他沒有幫助。若整欄其實是可讀的自然語言，這個判斷要重做。「Alarm Effects 的全欄值域」因此列為階段零的抽樣項目。
- 第三輪審查有一個視角指出 Alarm Effects 其實是「現場先看到現象、再反推代碼」的反向查詢入口，很有價值。**正因為有價值，更不該塞進語意不符的既有欄位**——它值得一個自己的欄位與一份縮寫對照表，而那是另一個獨立需求，不在本方案範圍。本輪的處理是明確記錄「已知、有價值、本輪不匯入」，而非默默忽略。

#### 4.4 `device_model` 的來源（第三輪審查發現的硬傷）

`_bulk_import_validate()` 的第一道防線就是機種存在性檢查，標準 alarm dict 也要求 `device_model`。但 LINE 3 這 10 個表頭欄位**沒有任何一欄是機種**。

v2 並非沒看到這個欄位——它在「現有程式碼」一節明確寫了 `grid_to_rows()` 的輸出「缺少 `device_model`、`description`、`solution` 等欄位…必須先解決這個轉換問題」。v2 漏掉的是**這個必填值在原廠檔案裡根本沒有來源**，因此把它當成可以在實作階段處理的格式轉換問題，而它實際上是 Route A 連第一道驗證都過不了的前提。

本輪建議：**由匯入時的 UI 指定，每個檔案對應一個機種**，預設值從檔名（`22062QE6SP63_LF` 等）解析後帶出，但必須由操作者確認、不得靜默採用。檔名解析規則需要在階段零由懂產線的人確認（檔名的哪一段是機種、哪一段是站別或版本）。若一份檔案內含多個機種的警報，這個假設就不成立，階段零必須驗證。

#### 4.5 跨檔案代碼碰撞（第三輪審查發現的硬傷；重複數已於第三輪查證修正實測）

5 份檔案要匯進同一個部門。**本輪已用 `openpyxl` 逐檔讀取 `Alarm Type` + `Alarm Number` 組合，5 份檔案共 214 筆資料，跨檔重複數＝0**（關鍵事實四）。這個系統的歷史事故正是代碼碰撞，因此這個結果值得記錄，但下面三項要求維持不變——0 是這一次這 5 份檔案的既有事實，不是這條路徑的保證，日後任何一份新檔案（含這 5 份之外，或這 5 份日後被原廠更新）都要重新檢查：

- 這次實測結果（重複數＝0）代表**目前這 5 份檔案不需要把機種或站別納入 `code` 組合規則**，`Alarm Type`+`Alarm Number` 本身已足夠識別，但這個結論綁定「這 5 份檔案」，不是通則。
- 階段二的純函式仍必須在轉出時偵測重複並**報錯中止**，不得靜默後蓋前——即使這次沒撞上，機制本身要在，服務的是這 5 份檔案以外的未來情境。
- preview 階段仍必須顯示跨檔案重複清單給操作者（這次預期清單為空，但顯示機制不能省略）。

#### 4.6 映射正確性的判定：誰說了算

第三輪互評一致指出：五個視角都說「映射表要先做」，沒有一份說「做完了怎麼知道對」。本輪補上：

1. **真相來源優先序**：原廠隨機文件／設備商說明 > 現場資深人員的既有認知 > 部門 admin 的目視判讀。目視判讀是最後一順位，不是唯一手段。
2. **交叉比對**：若其他部門已有同型設備的警報資料上線，拿轉出結果與之比對是成本最低的反向驗證。
3. **語言可用性**（第三輪互評發現）：已知**表頭是英文**；**欄位內容的語言尚未確認**——v2 只記載 Solution 欄「是完整的維修步驟文字」，沒記語言，內容可能是英文、中英混雜或中文。階段零抽樣時一併確認。**若**內容是英文，`solution` 原樣寫入後現場人員讀不懂，它在資料庫裡是完整的、卻是無效的，而 `completeness_report()` 只驗「有沒有填」、不驗「能不能用」——那時翻譯就是一個獨立且不小的工作項，應該在階段零就浮上檯面而不是上線後才發現。

### 五、事前門檻、事後留痕與 Kill Switch（本輪修正自指失效問題）

#### 5.1 v2 的 kill switch 是自指的，必須修正

v2 的設計是：`ENABLE_ROUTE_A_COMMIT` 預設關閉，「欄位映射通過硬性簽核流程」後才打開。但第二輪修訂已把該「簽核」降級為「部門 admin 在操作介面上點確認」——**操作者自己按下去就算通過**。開關的開啟條件指向一個由操作者自己完成的動作，這不是 gate。

同時，「留痕」只在**有人事後起疑**時才有價值，而語意錯誤的定義就是看起來完整合理、沒有人會起疑。用事後可追溯取代事前驗證，是範疇混淆。

#### 5.2 本輪的替代設計：一個真正的事前門檻 + 留痕 + 偵錯回路

**事前門檻（輕量、不變成簽核儀式）**：

- 映射表內容取 SHA-256，前 12 碼為版本識別。
- 若本次映射的雜湊與「上一次已確認並成功匯入」的雜湊**相同** → 操作者可一鍵沿用。
- 若**不同**（含首次） → UI 強制逐欄勾選確認，每一欄旁邊顯示該欄的前 3 筆真實內容節錄（見「七」）。不能一鍵沿用、不能跳過。
- 這個門檻仍然由操作者完成，沒有引入外部簽核人——但它把「無意識地重複按確認」變成不可能，這是在沒有獨立 QA 的小團隊裡能拿到的最實在的事前防線。

**Kill switch 的開啟條件必須是階段前置條件以外的事實，否則它不是 gate**。v2 的條件是「通過簽核」而簽核已被降級成操作者自己點確認；但若只是把條件改寫成「階段二・五已完成、測試已通過」，那也只是把階段表的前置條件抄一遍——階段三的程式碼寫得出來，這些條件必然早已滿足，開關交付即自動可開，gate 效力仍然是零。

因此開關的條件定為三項**新增的、可指出證據的事實**：

1. migration 007 已在正式環境執行，且完成一次 `commit_rows()` → `undo_snapshot()` 的實地還原驗證，**驗證結果有書面記錄**（見 5.3）。
2. canary 檔（`LF.xlsx`，4 筆）的每一筆已由現場人員**逐筆目視核對**，核對結果記在 5.5 的回報表裡——不是「沒有人回報問題」，而是「有人看過並記下來說對」。這兩者的差別就是整個 F9 的重點。
3. 階段二・五 其餘 4 份檔案匯入後，現場使用滿一段議定期間，回報表沒有新增映射相關的異議。

**開關狀態必須在 Route A 匯入頁面上可見**：顯示「此路徑尚未啟用」以及上述三項中尚未達成的是哪一項。一個只存在於 `.env` 的預設關閉開關，本身就是 migration 007「寫了但沒人記得啟用」的同構物；把狀態與未達成條件顯示在 UI 上，才是真的用機制取代「靠人記得」。開關關閉時端點回傳明確錯誤訊息（「這條匯入路徑尚未通過語意映射驗證，暫不開放」），不是靜默 404。

**條件 2、3 有一個順序上的硬要求**：它們都依賴 5.5 的「資料來源標註」與「現場回報入口」。這兩項若排在階段三，就會變成「判斷能不能做階段三，要等階段三做完」的循環。因此**這兩項前移到階段二・五**——它們不依賴 Route A 的 commit 端點，只需要在警報詳情頁加一行來源文字與一個回報按鈕。沒有回報入口，「無異議」只是靜默，不是證據。

#### 5.3 migration 007 必須先獨立驗證（本輪最高優先的既有風險）

v2 把 Route A 的回溯稽核與復原完全建立在 `import_snapshots` + `undo_snapshot()` 之上，同時自己承認這套機制「寫好但長期未在正式環境執行/驗證」。用沒測過的安全帶去解鎖更快的車速，順序是反的。

依本輪的階段劃分，**第一次真的把它當成退路的是階段二・五**（LINE 3 走 Route B 把資料寫進正式環境，出錯時就靠它整批退掉），Route A 之後更是完全建立在它之上。所以這件事的時程前置得比 v2 想的還早。

**這件事與走哪條路線無關**——Route B 現有的復原也靠它。因此獨立於本方案，應先在正式環境跑一次完整的 commit → `undo_snapshot()` → 確認資料真的還原。這是半小時的工作，卻是整個第五章的地基。

#### 5.4 回溯稽核（階段三）

- Route A 新 commit 端點寫入的每一筆資料，要能追溯回「哪次匯入、由哪個部門 admin、用哪個映射規則版本產生」。比照既有 `ImportSnapshotStore` 的模式寫入快照，並在 metadata 額外記錄：操作者帳號、確認時間、**完整映射表 JSON + 其 SHA-256 前 12 碼**、來源檔名。
- **為什麼存完整 JSON 而不只存版本號**（v2 待定項 3 的本輪定案）：人工遞增的版本號會漏更新，這正是「靠人記得」的失敗模式；而只記版本號、映射內容另外查程式碼歷史，查不到「操作者在 UI 上臨時改過的映射」。內容雜湊自動反映任何變動，而且可以直接餵給 5.2 的「是否強制逐欄確認」判斷，一物兩用。
- 快照格式必須相容於既有 `undo_snapshot()`（`commit.py:122` 起），不得自創一套。

#### 5.5 匯入後的偵錯回路（第三輪互評發現的完整缺口）

v2 談了匯入前的閘門與匯入後的復原，**完全沒有談「錯誤如何被發現」**。這是整份方案最大的邏輯斷點：語意映射錯誤會靜默通過所有檢查，留痕只在有人起疑時有用，而沒有人會起疑。

本輪新增三項，成本都很低，**而且前兩項必須在階段二・五 之前完成**（理由見 5.2 末：kill switch 的條件依賴它們，排在階段三會造成循環）：

1. **資料來源標註**（階段二・五 前）：警報詳情頁顯示這筆資料的來源（原廠檔名 + 匯入日期）。現場人員看到可疑內容時，能說得出「這是哪來的」。
2. **現場回報入口**（階段二・五 前）：警報詳情頁加一個「這筆資料不對」的回報按鈕，寫進一張簡單的回報表。這是唯一能讓語意錯誤主動浮現的機制——比前面所有防線加起來都更接近真實世界。
3. **Canary 上線**（階段二・五 內）：先只匯入 1 份檔案（建議 `LF.xlsx`，只有 4 筆，全錯也容易收拾），請現場逐筆目視核對並把結果記進回報表，再匯其餘 4 份。「逐筆看過並記下來說對」跟「沒有人回報問題」是兩回事，後者在沒有回報入口時只是靜默。

**並且必須誠實記錄一件事**：`undo_snapshot()` 復原得了 `alarms` 表，復原不了現場人員已經照錯誤處置動過的設備。因此真正的防線在匯入前的映射正確性與上線後的偵錯回路，不在事後復原。整個第五章只蓋住了比較不痛的那一半。

### 六、測試策略

#### 6.1 資料機密性確認記錄

這 5 份檔案放進 repo 當測試 fixture，由使用者本人於 2026-09-18 明確確認可以（透過顧問轉達），依據是內容為設備警報代碼、原因、處置方式（廠務/工程性質的技術文件），不含個資、財務資料或其他業務機密。這是資料所有者對自身資料性質的判斷與授權，不是工程端自行認定。**若之後有其他部門的類似情境，需要每次重新取得資料所有者的授權確認，不得援引本次先例當作通則。**

#### 6.2 正向測試（5 份真實檔案）

放進 `tests/fixtures/`（或依專案既有慣例），每份檔案至少驗證：

- 新的精確表頭組合比對分支找到正確的表頭列（用本文件表格的列數斷言）。
- Operating Modes 子欄位的數量與名稱正確——**以開頭表格第三輪查證修正後的實測值為準**（LF: PROD/MM；02: PM/ES/LT/VHP/EA/CL/MM；DE/RI/DB_01: PREP/PROD/PE/MM/CS/VHP），且**欄範圍由合併儲存格決定**（構造一份 Operating Modes 後面還有其他欄的變體檔案來驗證右邊界）。
- 轉出的 rows 筆數符合期望值——**以開頭表格第三輪查證修正後的實測值為準**（LF: 4、02: 92、DE: 20、RI: 95、DB_01: 3），這些已是逐列精算後的數字，不是估算值。
- 抽查代表性資料的欄位內容轉換正確：Operating Modes 全部啟用的、只啟用一個的、**全部未啟用的（驗證 `[]` 而非 `null`）**、以及含非 `x`/`-` 異常值的（若存在，驗證會產生解析警告而非靜默丟棄）各一筆。

#### 6.3 負向與迴歸測試（v2 完全沒有，本輪新增）

v2 的測試策略只有 happy path，而 fixture 就是設計時看的那 5 份檔案——這是同義反覆，不是驗證。新增：

- **既有行為迴歸**：拿 FILL203 那類既有檔案跑一遍，斷言新分支**不觸發**、既有兩段式邏輯的結果與改動前完全一致。這是唯一能證明「不影響既有行為」的東西，成本約一小時。
- **圖例誤判防護**：構造一份在真表頭之前放置「逐欄複述欄位名稱的圖例區塊」的檔案，斷言偵測仍然找到真表頭（驗證條件 B 的後置資料驗證與條件 C 的選擇規則確實生效）。
- **跨部門 schema 迴歸**（審查發現 F7，屬**階段三**）：`operating_modes` 進入 `ALARM_FIELDS`/`OPTIONAL_FIELDS` 影響的是所有部門共用的 schema 與 Route B 路徑。必須斷言既有部門的 Route B 匯入行為完全不變，特別是「欄位缺席時不覆蓋既有值」的既有語意沒有被新欄位破壞。
- **代碼碰撞**：構造兩份含相同 `code` 的檔案，斷言轉出時報錯中止而非靜默後蓋前。

### 七、欄位對應確認介面（階段三，本輪定案 v2 待定項 4）

- **並列呈現，且必須顯示真實內容**：左側是原廠表頭名稱 **加上該欄前 3 筆真實資料節錄**，右側是標準欄位的下拉選單。只顯示欄位名稱的介面，讓操作者變成在做「欄位名稱翻譯」，抓不到語意錯誤——真實內容才是判斷「這欄到底是原因還是處置」的依據。
- `device_model` 為必填欄位，從檔名帶出預設值，但必須由操作者確認（見 4.4）。
- **明確列出「本輪不匯入的欄位」**（Alarm Simulation / Alarm Effects / Alarm Reset / Validation Test），讓操作者看見它們被刻意丟棄，而不是靜默忽略。
- 映射雜湊與上次已確認版本不同時，強制逐欄勾選確認（見 5.2）。
- preview 階段顯示：跨檔案代碼重複清單、Operating Modes 解析警告、完整度攔截結果。

**階段二・五**：
- 前端（**必須先於匯入完成**）：警報詳情頁的資料來源標註、現場「這筆資料不對」回報入口與其回報表

- 轉檔腳本不進主線；前端兩項要進

- 前端：欄位對應確認介面、警報詳情頁的運行模式顯示

**與本方案無關但必須先做**：正式環境驗證 migration 007 的 commit → undo 還原，並留下書面記錄（見 5.3）。

## 第三輪審查發現（逐條）

以下每一條都對應上文的具體修正，列出以便日後回查判斷依據。

**F1（已修正，見 1.1）** v2 把高確信的新分支排在低確信的 fallback 之後，順序反了。

**F2（已修正，見 1.2；本輪修正過程中一度自行踩到同一個坑，見下）** v2 的新分支沒有等價於 `MIN_CODE_ROWS` 的後置驗證，且取「第一個命中列」。而這些檔案前段就有「代碼圖例」「運行模式圖例」區塊，圖例最常做的事正是逐欄複述欄位名稱——這是最可能誤命中的地方，v2 完全沒防。另：v2 的機率論證（「多個精確片語同列出現的巧合機率本質上遠低於單一寬鬆詞」）被用來取代防呆設計，而有效樣本量實質是 1（5 份檔案同一原廠同一模板）。

**F3（已修正，見二）** Operating Modes 子欄位「從該欄往右的所有非空儲存格」沒有定義右邊界；合併儲存格範圍這個已讀出的資訊沒被用上。另補上 `x`/`-` 以外的值不得靜默丟棄、`[]` 與 `null` 必須區分。

**F2b（本輪自行踩到、已修正，見 1.2「條件 B 的門檻為什麼不是既有的 MIN_CODE_ROWS」）** 本輪修訂稿最初把既有的 `MIN_CODE_ROWS`（≥5 列）原封搬進新分支的條件 B。但 `DB_01.xlsx` 表頭後只有 3 列資料、`LF.xlsx` 只有 5 列——這個絕對門檻會讓 DB_01 的真表頭永遠通不過、整份檔案偵測失敗，直接與 6.2 的正向測試相斥。已改為比例判準。記錄這一條，是因為它示範了 F2 指出的那種錯誤有多容易重犯：把一個在別處驗證過的閾值搬過來，而沒有對照自己文件裡的資料。

**F2c（本輪新增，見關鍵事實五與 1.2 末）** 條件 B 需要 `Alarm Number` 的代碼格式正規式，而這個資訊尚不存在。若不處理，階段一會隱性依賴階段二才產出的映射結論。已把它列為階段零產出項與階段一的前置條件。

**F4（已修正，見表格下方）** v2 表格的「真實資料筆數」對兩份小檔與三份大檔用了**不同公式**：小檔是「總列數 − 子表頭列」（5、3），大檔是「總列數 − 表頭列」（`~93`、`~21`、`~96`，各多算一列）。而且兩種公式算出來的都只是「剩餘列數」，未扣除尾端空白或註解列。v2 雖已註明部分筆數是估算值、實作前需重算，但仍把它列為回歸測試的期望值來源，也沒有指出公式本身不一致——本輪把公式統一，並明確禁止直接拿來當斷言基準。

**F5（已修正，見四）** 映射表被寫成「硬性 release gate」，但那張表不存在。一個沒有內容的關卡擋不了任何東西。五個審查視角對此一致。

**F6（已修正，見 4.4、4.5）** 兩個硬傷：(a) `device_model` —— v2 指出了 `grid_to_rows()` 缺這個欄位的 schema 落差，但沒有追問這個必填值在原廠檔案裡**根本沒有來源**，因而把它當成實作階段可解的轉換問題，實際上是 Route A 連第一道驗證都過不了的前提；(b) 5 份檔案匯進同一部門的跨檔 `code` 重複問題，v2 零字提及，而這個系統的歷史事故正是代碼碰撞。

**F7（已修正，見 6.3）** v2 在設計層級指定了 `operating_modes` 歸 `OPTIONAL_FIELDS` 的相容語意（缺席不覆蓋既有值），但沒有任何測試去驗證它，也沒有評估這個**跨部門共用** schema 變更對既有上線資料的影響半徑。

**F8（已修正，見 5.1、5.2）** kill switch 的開啟條件自指：要「通過語意映射驗證」才開，而第二輪修訂已把該驗證降級為部門 admin 自己在 UI 點確認。而且一個只存在於環境變數的預設關閉開關，本身就是 migration 007「寫了但沒人記得啟用」的同構物。**本輪修訂稿最初把條件改寫成「階段二・五完成、測試通過」，但那只是把階段表的前置條件抄一遍——階段三寫得出來這些就必然滿足，gate 效力仍是零。已改為三項階段前置條件以外、可指出證據的事實。**

**F9（已修正，見 5.5）** 整份 v2 沒有回答「錯誤如何被發現」。語意錯誤會靜默通過所有檢查，留痕只在有人起疑時有用，而沒有人會起疑。缺 canary、來源標註、現場回報入口。本輪並把來源標註與回報入口前移到階段二・五，否則 kill switch 的條件會依賴階段三的產物而形成循環。

## Council 結論：LINE 3 原廠 Excel 匯入方案 v2 壓力測試（外部審查，2026-09-20）

### 共識

五個視角獨立收斂到四點，信心高：

1. 映射表不存在，卻被當成 release gate。整份方案的偵測、commit、快照、kill switch 全部繞著一張空表建，順序反了。
2. `import_snapshots` 未在正式環境驗證，卻是所有安全機制的地基。用沒測過的安全帶去解鎖更快的車速。
3. 交付該拆。無人認為現狀的綁定式交付合理。
4. 測試是同義反覆。fixture 就是設計時看的那 5 份檔案，全 happy path，筆數還停在 ~93、「需再核對」。

### 分歧

真正的對立是「擴張者」對其餘四個視角：這次該擴張還是該收縮。擴張者主張把映射表做成可複用的原廠 profile、kill switch 當 feature flag 基礎設施、Operating Modes 做成情境化查詢；其餘四份（互評也一致）判它盲點最大，因為所有提案都建立在「映射是對的」這個尚未成立的前提上——把錯誤語意資產化，是把一次錯誤放大成平台級錯誤。這個判讀已在 v3 的 F15 記錄完整理由，避免日後重新發明。

第一性原理視角更進一步主張「LINE 3 只轉一次，直接手動轉檔走 Route B，Route A commit 等第二家原廠出現再說」。這跟使用者已下的裁決衝突，未逕行推翻，而是在 v3 用「階段二・五」把它的風險論證吸收進來：LINE 3 這次上線走既有 Route B（轉檔由程式做，不是人工複製貼上），Route A 的 commit 端點延後到階段三。完整反方論證保留在 F16，若使用者要改裁決，那是最好的依據。

### 互評抓到的盲點

三個五份初評全漏的：匯入後沒有偵錯回路（所有人都在談匯入前的閘門與匯入後的復原，沒人談「錯誤如何被發現」——而語意錯誤的定義就是看起來合理，沒人會起疑）；誰判定映射是對的、判準是什麼（真相來源應是原廠文件或設備商，不是 admin 目視）；既有部門的爆破半徑（`operating_modes` 進 `ALARM_FIELDS` 動的是跨部門共用 schema）。

另外局外人視角問出三題，只有它問到，卻是硬傷：`device_model` 從哪來？（10 個原廠欄位沒有一欄是機種）`code` 怎麼組？5 份匯進同一部門、跨檔 `Alarm Number` 重複怎麼辦？（而歷史事故正是代碼碰撞，v2 零字提及）。

### 審查者自行發現的額外問題

- 表格筆數用了兩套公式。LF 與 DB 寫 5、3 是「總列數 − 子表頭列」；02/DE/RI 寫 ~93/~21/~96 是「總列數 − 表頭列」，各多算一列（漏扣子表頭）。已算過確認。
- Operating Modes 子欄位沒有右邊界。v2 寫「從該欄往右的所有非空儲存格」——合併範圍 J58:K58 這個資訊文件自己已經讀出來了卻沒拿來用。這 5 份剛好它是最後一欄所以沒出事。
- `[]` 與 `null` 沒區分。「所有模式都不啟用」與「這檔沒有這欄」在 `OPTIONAL_FIELDS` 的不覆蓋邏輯下會撞在一起，而測試策略本來就要求挑一筆「都沒啟用的」。
- `x` 以外的值靜默丟棄。沒定義大小寫、全形、✓、備註文字怎麼辦，而靜默丟棄等於把「會觸發」默默變成「不會觸發」。
- v3 初稿自行踩了 council 指出的同一個坑：條件 B 照抄既有的 `MIN_CODE_ROWS`（≥5 列），而 `DB_01.xlsx` 只有 3 筆資料，那會讓它永遠偵測失敗。查核時抓到了，已改成比例判準，並在 F2b 記下這個反例。

### 建議

尊重原裁決（原生支援照做），但拆成階段零／一／二／二・五／三，把寫入風險往後推、把低風險的解析能力先放出來。kill switch 的開啟條件改成三項階段前置條件以外、可指出證據的事實，並要求開關狀態在 UI 上可見——否則它就是 migration 007 的同構物。偵錯回路的前兩項（來源標註、回報入口）前移到階段二・五，不然「能不能做階段三」要等階段三做完才知道。

### 第一步

今天寫一支 openpyxl 腳本，抽出 5 份檔案每欄的實際值、逐列精算真實筆數、算出跨檔 `Alarm Type`+`Alarm Number` 的重複數、確認 `device_model` 的來源。無程式碼變更，1–2 小時。

這張表出來之前其他決定都是空談；出來之後，`Alarm Type` 到底是 `severity` 還是 `code` 前綴、`HMI Message` 跟 `Alarm Description` 哪個是 `cause`，會自己現形。
