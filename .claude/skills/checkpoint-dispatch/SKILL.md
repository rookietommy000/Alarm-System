# Checkpoint Dispatch（自我校準與派工情境包）

多輪對話後，模型對「離目前位置越近」的內容給予的注意力權重，通常明顯高於一開始的系統指令與角色設定（近因偏差）。對話輪數一多，最前面訂好的 [RULES.md](../../../RULES.md) 就被中間的除錯來回稀釋，即使仍在上下文視窗裡，也更容易依「剛做過的事」而非「一開始該怎麼做」生成下一步。

徵兆：同一錯誤重複發生（即使剛被糾正過）、忘記已拍板的規則或步驟順序、回「馬上改」但下一步照舊、多輪後回答範圍偏離最初任務。這是狀態被污染，不是理解問題——跟它講道理無效，要用結構化手段重置。

此 skill 只適用於 PM 這個角色自己的執行紀律，不要求其他 peer session 遵守（peer 各自的行為規範不由 PM 決定）。

## 1. 每次回覆使用者前先印 Checkpoint 行

第一行固定格式：

```
[階段：Bucket X] [路由：老師|醫生|員工|QA|使用者|無] [任務：<一句話>]
```

這行不是裝飾——印這行之前，先回頭確認 RULES.md 這次動作屬於哪個 Bucket、要不要路由給誰，再生成答案。若這行跟使用者預期的階段對不上，就是偏離訊號，直接進入第 3 節第一層處理。

## 2. 每次 SendMessage 派工前附完整情境包

呼叫老師／醫生／員工／QA 時，不能只丟任務內容，要附上對方的角色定位與本次任務的完整背景——對方不會記得自己在整個協作裡的定位，尤其是新開的 session。固定格式：

```
【角色】：<老師|醫生|員工|QA>
【角色職責邊界】：<摘自 RULES.md 第0節該角色那一列，或已知的硬邊界，如醫生「從不commit/push」>
【本次任務】：<具體任務內容>
【已知狀態／上次檢查點】：<上一輪結果或待銜接狀態，沒有則寫「無」>
```

這是每次派工的固定成本，不是可省的步驟——少附一次，對方就可能用錯流程或漏職責邊界。

## 3. 狀態異常升級流程

發現 PM 自己或某個 peer 開始鬼打牆，依序升級，同一層不重複超過一次：

- **第一層｜強制指令覆寫（單次）**：
  ```
  [強制指令]：停止當前處理，重新讀取 RULES.md 與本次任務的派工情境包，拋棄前面的錯誤嘗試，從指定步驟重新開始。
  ```
- **第二層｜果斷重啟**：同一類錯誤在第一層之後再犯一次，立即建議使用者重開該 session 或換一個乾淨的對話，不要進入第三次糾正的迴圈。

PM 對 peer session 異常訊號的回報門檻仍依 RULES.md 第4節「同一 peer、同一類、同一工作流滿兩次才提醒使用者」執行，本節不降低那個門檻——第一層強制指令是 PM 自己當場處理的動作，不等於已經觸發要回報使用者的門檻。

## 4. 技術澄清（避免混淆）

Claude Code 的 `hook`（`settings.json` 裡的 `UserPromptSubmit`／`SessionStart` 等）是系統層級自動觸發 script 的機制，且只能掛在自己這個進程上，技術上無法跨進程監控其他 session。本 skill 第1節的 Checkpoint 行是寫進行為規則、由 PM 自己每次執行時主動輸出，不是系統自動攔截，不要用「hook」稱呼這個機制。

## 適用範圍之外

- 不要求老師/醫生/員工/QA 也印 Checkpoint 行或遵守此 skill——這是 PM 自己的執行紀律，不是要求 peer 配合的協議，避免增加其他 session 的負擔。
- 任務本身很小、單輪就能完成時，Checkpoint 行仍要印（成本極低），但不需要額外觸發升級流程判斷。
