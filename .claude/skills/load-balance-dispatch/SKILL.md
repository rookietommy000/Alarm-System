# Load Balance Dispatch（負載平衡分派紀律）

多 session 協作時，很容易把整條工作鏈的責任都疊在同一個人身上（例如「commit 一律走員工那條線」導致所有前置準備工作也不自覺地都排給員工做），而其他人閒置等待，直到輪到他們那一棒才開始動。這個 skill 是給統籌者（顧問角色）在分派任務時要遵守的紀律：**任何時候發現一人忙、多人閒，要主動拆解任務並重新分工，不要等使用者提醒才想到。**

## 觸發時機

任何時候你手上有一份多步驟/多子任務的工作要分派下去，且團隊裡有兩個以上的 session 時，都適用。不需要使用者觸發，這是背景執行原則。

## 執行紀律

1. **分派前先問自己：這份工作裡，有沒有能拆給不同人「同時做」的部分？**
   - 常見的可拆分模式：實作 vs 驗收準備（QA 可以先設計測試情境，不用等 code 寫完）、實作 vs 複核（另一人可以先評估潛在陷阱/邊界情況）、多個獨立子任務（互不依賴的可以平行分給不同人）。
   - 固定角色分工（例如「commit 一律走某人」）只限制**最終落地的那個動作**，不代表這個人前面的所有準備工作都要他一手包辦。準備、設計、驗證這些前置/並行工作可以分給別人，只有真正需要那個角色權限/職責的最後一步才收斂回去。

2. **分派後盤點一次：現在誰在忙、誰在等？**
   - 如果盤點結果是「一人在做、其餘都在等對方做完才能動」，這就是失衡狀態，要立刻重新拆分，不要等對方做完整份工作才發現其他人根本沒事做。
   - 判斷「等」是不是必要的：如果後面的人真的要依賴前面的產出才能開始（例如沒有 schema 就無法寫測試），那是合理依賴，不用硬拆；但如果只是「習慣上這個人先做」而非「技術上必須先做」，就要拆開。

3. **重新分工時，明確交代「三邊不互相卡住」的邊界。**
   - 每個人拿到任務時要清楚知道：自己這塊不依賴誰、可以馬上開始；以及最後誰負責統整銜接。
   - 例如：一人做核心實作，另一人同時設計驗收情境/重現腳本（不用等實作完成才開始想怎麼測），第三人同時評估潛在陷阱或複核設計（不用等 code 寫完才開始看）。

4. **不要為了拆分而拆分。**
   - 如果任務本身就小、單人就能快速完成，不需要刻意找理由拆給多人做，那樣反而增加溝通成本。
   - 拆分的判準是「總完成時間會不會因為平行處理而縮短」，不是「人越多越好」。

## 反面案例（不要這樣做）

> 四項任務，因為「commit 一律走員工那條線」的既有原則，就把四項任務的設計、實作、測試準備全部排給員工一個人做 → QA、醫生全程閒置等通知 → 使用者發現後問「讓其他沒事的人去幫忙啊」→ 才想起來重新拆分

正確做法：分派前就先想清楚每項任務裡哪些部分可以平行進行，只把「真正需要走那條線」的最後一步（例如實際 commit）收斂到固定角色，其餘準備/設計/驗收情境的部分主動分給空手的人，讓使用者在還沒開口提醒之前，就已經看到多人同時在動。

## 適用範圍之外

- 這不是要求每次分工都湊齊所有人一起動——如果任務本身就是單人可以獨立、快速完成的小事，不用刻意拆分找事給別人做。
- 「固定角色收斂到一人」的規則（例如 commit 一律走某人）本身是對的、要繼續遵守，這個 skill 要修正的是「誤以為固定角色也要求這個人包辦所有前置工作」這個常見的過度延伸，不是要推翻固定角色本身。

## 彈性調度是任務範圍內的暫時授權，不是永久改變分工

如果使用者明確授權「這次任務的分配由你彈性安排」，這代表**當下這個任務的具體工作內容分配**（誰做設計評估、誰準備驗收、誰複核、誰動手）可以不拘泥於團隊原本各自的角色定位。但這個授權有兩個邊界：

1. **硬性規則不受影響**：像「commit/push 一律走特定人」這類已經定案的硬性規則，即使被授權彈性調度，也不能一併鬆動，除非使用者明確把這條規則也一起授權出去。
2. **任務結束要復原**：這是針對當下任務的暫時性調度，不是把團隊原本的角色分工永久改掉。下一輪新任務開始時，要重新回到原本的角色分工起點（例如老師負責設計評估、QA 負責驗收、員工負責實作），不要把上一次的臨時調度當成新常態延續下去。如果不確定某次任務是否已經結束、是否該復原，直接問使用者。
