# Async Dispatch（非同步分派紀律）

多 session 協作時，發送 SendMessage 給 peer 後很容易陷入「原地等回覆」的狀態——尤其是彙整多人查證結果準備彙報時，會不自覺把整個任務卡在某一個未回覆的訊息上。這個 skill 是給統籌者（顧問角色）在**每一次**發出需要對方回覆的 SendMessage 後要遵守的紀律。

## 觸發時機

任何時候呼叫 `SendMessage` 給 peer session、且預期對方會回覆時，都適用。不需要使用者觸發，這是背景執行原則。

## 執行紀律

1. **發送後立刻問自己：這個回覆是不是我下一步唯一能做的事？**
   - 如果不是（例如還有其他 peer 的分析可以先整理、還有文件可以先草擬、還有其他人的訊息可以先回），**立刻去做那些事**，不要停在原地等。
   - 只有當回覆是繼續前進的**唯一**依賴時，才允許暫停等待——即使如此，也要先確認手上沒有其他任何可以推進的事。

2. **彙整任務要用「已到齊的先寫、缺的先標記」的方式推進，不要等全員到齊才動筆。**
   - 例如整理問題文件給專家時：老師的方案先寫進去、QA 查到一半的部分先標「（查證中，待補）」，不要因為一個人沒回覆就讓整份文件停擺。
   - 之後對方回覆了，直接補進去即可，不影響已完成的部分。

3. **如果某個回覆確實卡在關鍵路徑上（沒有它無法繼續），要主動追蹤，不能無限等待：**
   - 送出訊息後，如果因為其他任務被打斷、一段時間沒收到回覆就要回頭確認，主動送一次簡短的催辦訊息（不用道歉或解釋太多，一句「進度如何/卡在哪」即可）。
   - 催辦後如果還是沒回應，且已有足夠資訊可以先給出部分結論，就先給部分結論並標註缺口，不要繼續空等。

4. **不要讓使用者發現「卡住」比自己先發現。**
   - 這是最重要的訊號：如果使用者需要提醒你「怎麼還沒好」、「他在睡覺嗎」，代表紀律已經失守。統籌者應該在使用者開口之前，就已經注意到某個環節卡住並採取行動（催辦或先出部分結果）。

## 反面案例（不要這樣做）

> 發訊息給 QA 要她查一個資料庫欄位 → 什麼都不做，等她回覆 → 使用者過了一段時間問「好了沒」→ 才想起來去催 → 使用者又問「他在睡覺嗎」→ 才真的去處理

正確做法：發訊息後應該立刻轉去處理其他人已經回報的分析、把問題文件的其他段落先寫好，過一段時間沒收到回覆就主動催一次，催了還沒回應就先用「待補」標記出一版可用的文件。

## 適用範圍之外

- 這不是要濫發催辦訊息——只在真的卡在關鍵路徑、且已經過了合理等待時間才催。
- 不要因為這個 skill 存在，就把每個任務都拆成「先給部分結果」——只有在等待造成整體進度停滯時才需要這樣做，正常的分工回報不需要刻意提前截斷。
