# TFM001 抽取正確率量測（2026-08-24）

`EXTRACTION_SPEC.md` 第7節「正確率量測」的實測結果。原本第7節記錄
`警報001.pdf` 對照 ACM002/DTS003-BL-A420 皆零命中、無 ground truth
可用——後續核對發現 `data/backup/other/TFM001/警報001.pdf` 所在資料夾
名稱本身就是線索，比對 `data/backup/TFM001.json` 後確認**這份 PDF
就是 TFM001 的手冊**（代碼、標題、cause 內容、元件編號全部對得上，
且代碼編號未被重新編號，不像先前誤判的 ACM002 那樣）。

## 方法

1. `parse_alarms.py --rasterize` 把 8 頁光柵化成 PNG
2. 逐頁送 `EXTRACTION_SPEC.md` 第4節的抽取 prompt（Gemini）
3. **逐筆肉眼核對原圖**（不是只做文字比對——文字比對曾經導致誤判，
   見下方「比對方法的教訓」）

| 問題 | 案例 | 說明 |

| 簡繁轉換 | `0139` | AI 輸出「冷**却**板」，原圖是「冷**卻**板」（簡體字混入，違反「不得改寫」規則） |

其餘 76 筆（含數十處元件編號 `B42.0`/`F43.1`/`M53.0`/`QF46.1`/`K120.6`
等）逐字正確，零幻覺、零遺漏、零元件編號錯誤。

`0174` 正確標記 `has_figure: true` + `uncertain: ["figure_not_extracted"]`
（該筆確實附有裁切迴圈示意圖）。

`0054` 的綠底手動加註「E1」，文字內容正確保留，但**沒有標記為
`handwritten`**——規格要求標而漏標，非內容錯誤，值得在 prompt 裡加強

## 意外發現：既有資料庫本身壞損，而非原文有問題

比對時發現多筆 DB 內容是亂碼，但原圖清楚乾淨：

| `0025` | cause | 整段亂碼 `BARRE 1 EBB AB HG...` | 正常英文句 |
| `0081` | description | `Ais} E RRSP AN` | 裁切站區域安全控制裝置點位異常 |

比既有資料庫更乾淨。

同時確認 `0003`/`0004`/`0006`/`0008` 原圖上存在但 `TFM001.json`
完全沒收錄，是真正的資料缺口。

## 比對方法的教訓

第一輪只用文字比對（AI JSON vs DB JSON 逐欄位比對），得出「DB 缺
0003/0004/0006/0008 這4筆」「AI 漏抓23筆中文標題」兩個結論——**兩者
都是錯的**。肉眼看過原圖後才發現：那4筆原圖上確實存在（是 DB 漏收
錄，不是 AI 幻覺或缺失）；那23筆裡至少核對過的部分是原圖本身就沒有
中文（AI 判斷 `title_zh: null` 是對的，DB 的中文是後補翻譯）。

**純文字比對無法驗證「谁对谁错」，只能告訴你「哪裡不一樣」——要判斷
不一樣的哪一方是對的，必須有第三方真相（這裡是原圖）介入。**

## 全庫亂碼掃描：嘗試失敗，未產出可用清單

嘗試寫 regex 掃描 TFM001 以外的機種（ACM001/ACM002/PILM003 等）找
同類亂碼，兩次嘗試：
- 規則太寬：把正常的英文大寫標題（如 `MAIN POWER CUT 主電源切斷`）
  大量誤判成亂碼（ACM001 誤報 135 處）
- 規則收緊後：只抓到 3 處，且跟已知的 TFM001 案例特徵重疊度低，
  可信度不明

**結論：這類亂碼沒有穩定的文字特徵可用簡單 regex 可靠偵測**，靠猜
regex 找不出可信的清單。比較務實的路徑是等 `inspect`/抽取功能做出
來後，比照這次「AI 重新抽取 vs 既有 DB」的方法逐機種跑一輪（前提是
原始文件還在），而非規則掃描。
